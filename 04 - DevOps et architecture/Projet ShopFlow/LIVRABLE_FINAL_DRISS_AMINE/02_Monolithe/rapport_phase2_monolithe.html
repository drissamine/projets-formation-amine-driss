Respect de la structure DDD et architecture en couches hexagonales.

1. Structure du Projet (Layered Architecture)

Le code est organisé par domaine (Bounded Context) puis par couche fonctionnelle.

src/modules/
└── orders/
    ├── domain/          [Invariants, Entities, VOs]
    ├── application/    [Use Cases, OrderService]
    ├── infrastructure/ [Prisma Persistence]
    └── interfaces/     [Express Controllers/Routes]

2. Documentation des API Endpoints

POST /api/auth/register Inscription client
POST /api/auth/login JWT Authentication
GET /api/products Catalogue filtrable
POST /api/products Ajout produit (Admin Only)
POST /api/orders Passage de commande
GET /api/orders/:id Suivi de commande
POST /api/payments Simulation transaction

3. Modèle d'Architecture Logique

graph TD UI[Clients / UI] subgraph "Monolith Engine" Routes[Express Router] Auth[JWT Middleware] subgraph "Modular Boundary: Users" UC_U[Auth Service] DM_U[User Entity] end subgraph "Modular Boundary: Orders" UC_O[Order Service] DM_O[Order Aggregate] end end DB[(PostgreSQL Prisma)] UI --> Routes Routes --> Auth Auth --> UC_O UC_O --> DM_O UC_O --> DB

4. Patterns Techniques Implémentés

  • Validation Zod : Schémas stricts pour chaque entrée utilisateur.
  • Repository Pattern : Abstraction de Prisma pour permettre un changement de DB sans toucher au Domaine.
  • Security : Hachage Bcrypt pour les mots de passe et signature HS256 pour les Tokens.
  • Inter-Module : Communication directe (méthode d'objet) entre services (ex: OrderService appelle ProductService).
