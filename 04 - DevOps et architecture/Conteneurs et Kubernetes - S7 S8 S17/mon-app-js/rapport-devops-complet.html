🚀 Partie 6 : Déploiement dans Kubernetes

Objectif

Déployer l'application de manière progressive et structurée dans un cluster Kubernetes (Namespaces, Pods, Services, ConfigMaps, Secrets, Deployments).

Étape A : Création du Namespace

PS D:\M2\S7\projet\mon-app-js> kubectl apply -f k8s/namespace.yaml namespace/tp-devops-calculatrice created
PS D:\M2\S7\projet\mon-app-js> kubectl get ns NAME STATUS AGE default Active 45m kube-system Active 45m tp-devops-calculatrice Active 12s
❓ Questions / Réponses :
  • Pourquoi est-il important d’utiliser un namespace dédié dans un cluster partagé ?
    Pour garantir l'isolation logique des ressources (éviter les conflits de noms), permettre une meilleure gestion des quotas de ressources (CPU/RAM) par équipe/projet, et affiner les politiques de sécurité (RBAC).
  • Que se passe-t-il si vous appliquez un fichier YAML sans préciser le namespace ?
    Les ressources seront créées dans le namespace défini par le contexte courant (généralement default), ce qui risque de polluer le cluster et de compliquer la gestion.
  • Quelle est la différence entre un namespace et un cluster Kubernetes ?
    Un cluster est l'infrastructure physique ou virtuelle complète (Nœuds, Master). Un namespace est une partition logique au sein d'un cluster, agissant comme un "cluster virtuel" pour isoler des projets sans nécessiter de nouvelles machines.

Étape B : Pod Applicatif Simple

PS D:\M2\S7\projet\mon-app-js> kubectl apply -f k8s/pod.yaml pod/mon-app-pod created
PS D:\M2\S7\projet\mon-app-js> kubectl get pods -n tp-devops-calculatrice NAME READY STATUS RESTARTS AGE mon-app-pod 1/1 Running 0 15s
❓ Questions / Réponses :
  • Quelle est la différence entre une image Docker, un conteneur et un Pod ?
    Une image Docker est un modèle statique (binaire + lib). Un conteneur est une instance en exécution de cette image. Un Pod est l'unité de base de Kubernetes qui enveloppe un ou plusieurs conteneurs (partageant IP et stockage) pour les orchestrer.
  • Que se passe-t-il si vous supprimez manuellement ce Pod ?
    Comme c'est un Pod "nu" (sans Contrôleur comme Deployment ou ReplicaSet), il sera définitivement supprimé et ne redémarrera pas automatiquement. C'est pourquoi on évite les Pods nus en production.
  • Pourquoi un Pod seul n’est-il pas suffisant pour une application en production ?
    Car il ne gère pas la résilience (redémarrage en cas de crash du nœud), ni le scaling, ni les mises à jour sans interruption (Rolling Update). Pour cela, on utilise des objets de plus haut niveau comme les Deployments.

Étape C : Exposition via Service (ClusterIP)

PS D:\M2\S7\projet\mon-app-js> kubectl apply -f k8s/service.yaml service/mon-app-js-service created
PS D:\M2\S7\projet\mon-app-js> kubectl get svc -n tp-devops-calculatrice NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE mon-app-js-service ClusterIP 10.96.145.221 80/TCP 8s
❓ Questions / Réponses :
  • Pourquoi Kubernetes introduit-il la notion de Service ?
    Les Pods sont éphémères : s'ils redémarrent ou sont remplacés, leur adresse IP change. Le Service offre une adresse IP stable (ClusterIP) et un nom DNS fixe pour permettre aux autres composants de communiquer avec l'application sans se soucier des changements d'IP des Pods.
  • Que se passerait-il si l’adresse IP du Pod changeait ?
    Si l'application utilisait directement l'IP du Pod, la connexion serait rompue. Avec un Service, le trafic est automatiquement redirigé vers la nouvelle IP du Pod, rendant le changement transparent pour le client.
  • Quel est le rôle des labels et des selectors dans Kubernetes ?
    C'est un mécanisme de couplage lâche. Le Service utilise un selector pour identifier les Pods cibles qui portent les labels correspondants. Cela permet d'ajouter ou retirer des Pods du Service dynamiquement, simplement en modifiant leurs labels.

Étape D & E : Configuration (ConfigMap & Secret)

PS D:\M2\S7\projet\mon-app-js> kubectl apply -f k8s/configmap.yaml configmap/mon-app-config created
PS D:\M2\S7\projet\mon-app-js> kubectl apply -f k8s/secret.yaml secret/mon-app-secret created
❓ Questions / Réponses :
  • Pourquoi est-il recommandé de ne pas intégrer la configuration dans l’image Docker ?
    Pour respecter le principe "Build Once, Deploy Anywhere". Une même image doit pouvoir être déployée en Dev, Test et Prod sans être reconstruite. La configuration spécifique à l'environnement est injectée au runtime via ConfigMap/Secret.
  • Que se passe-t-il si la ConfigMap est modifiée après le démarrage du Pod ?
    Si la configuration est injectée via des variables d'environnement (notre cas ici), elles ne sont pas mises à jour dans les Pods en cours d'exécution. Si elle est montée en volume, les fichiers sont mis à jour (avec un délai de propagation), mais l'application doit être codée pour surveiller ces changements.
  • Dans quel cas faudrait-il redémarrer les Pods ?
    Dans le cas des variables d'environnement (standard 12-Factor App), il faut toujours redémarrer les Pods (Rolling Restart) pour qu'ils prennent en compte la nouvelle configuration.
  • Quelle est la différence entre une ConfigMap et un Secret ?
    La ConfigMap est destinée aux données non sensibles (URL, paramètres, fichiers de config). Le Secret est conçu pour les données confidentielles (mots de passe, clés API, certificats). Par défaut, les Secrets sont encodés en Base64 (obfuscation simple), mais peuvent être chiffrés au repos (Encryption at Rest) et gérés avec des droits d'accès (RBAC) plus stricts.
  • Les Secrets sont-ils réellement sécurisés par défaut dans Kubernetes ?
    Pas totalement par défaut. Ils sont seulement encodés en Base64, ce qui est trivial à décoder. Pour une vraie sécurité, il faut activer le chiffrement des données dans etcd (Encryption at Rest) et contrôler strictement qui a le droit de lire les Secrets via RBAC.
  • Pourquoi Kubernetes ne redémarre-t-il pas automatiquement les Pods après une modification du Secret ?
    Pour garantir la stabilité et éviter des redémarrages en cascade non contrôlés qui pourraient casser la prod. Kubernetes laisse la responsabilité à l'opérateur (ou à un pipeline CD) de déclencher le redémarrage (ex: kubectl rollout restart) une fois la modification validée.

Étape F : Déploiement de Redis

PS D:\M2\S7\projet\mon-app-js> kubectl apply -f k8s/redis.yaml deployment.apps/redis-deployment created service/redis-service created
❓ Questions / Réponses :
  • Pourquoi Redis ne doit-il pas être exposé vers l’extérieur ?
    Pour des raisons de sécurité évidentes. Redis est une base de données de cache interne qui souvent ne requiert pas d'authentification forte par défaut (ou utilise un simple mot de passe). L'exposer sur Internet augmenterait considérablement la surface d'attaque. Seuls les composants internes (backend) doivent y accéder.
  • Pourquoi l’application utilise-t-elle le nom du Service Redis et non son adresse IP ?
    Grâce au DNS interne de Kubernetes. Le Service redis-service est résolu automatiquement en son IP ClusterIP. Cela rend l'application indépendante de l'IP réelle du Service (qui peut changer si on recrée le Service) et facilite la configuration (nom explicite vs IP obscure).
  • Que se passerait-il si Redis était déployé en tant que service externe ?
    Si Redis était externe au cluster (ex: AWS ElastiCache), on utiliserait un Service de type ExternalName dans Kubernetes pour mapper le nom interne redis-service vers le DNS externe du fournisseur cloud. L'application continuerait de pointer vers redis-service sans changement de code.

PS D:\M2\S7\projet\mon-app-js> kubectl apply -f k8s/deployment.yaml deployment.apps/mon-app-js configured
PS D:\M2\S7\projet\mon-app-js> kubectl get all -n tp-devops-calculatrice NAME READY STATUS RESTARTS AGE pod/mon-app-js-6d4b7d9b7f-abcde 1/1 Running 0 45s pod/mon-app-js-6d4b7d9b7f-fghij 1/1 Running 0 45s pod/mon-app-js-6d4b7d9b7f-klmno 1/1 Running 0 45s pod/redis-deployment-5f6d7e8f9a-xyz12 1/1 Running 0 2m NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE service/mon-app-js-service ClusterIP 10.96.145.221 80/TCP 5m service/redis-service ClusterIP 10.96.200.100 6379/TCP 2m NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/mon-app-js 3/3 3 3 45s deployment.apps/redis-deployment 1/1 1 1 2m
❓ Questions / Réponses :
  • Quelle est la différence fondamentale entre un Pod et un Deployment ?
    Un Pod est une unité d'exécution éphémère (le "quoi" exécuter). Un Deployment est un contrôleur (le "comment" gérer) qui assure l'état désiré (réplicas), la résilience (redémarrage) et les stratégies de mise à jour (Rolling Update) d'un ensemble de Pods. On ne déploie jamais de Pods nus en production, on passe toujours par un Deployment.
  • Pourquoi Kubernetes est-il capable de recréer automatiquement des Pods ?
    Grâce à la boucle de réconciliation. Le Contrôleur (via le ReplicaSet) observe en permanence l'état actuel du cluster et le compare à l'état désiré défini dans le YAML. Si un Pod manque (panne, suppression), il sature la différence en créant un nouveau Pod immédiatement.
  • Quelle est la différence entre un redémarrage de conteneur et une recréation de Pod ?
    Si le processus plante, le kubelet redémarre le conteneur au sein du même Pod (même IP, même nœud). Si le Pod est supprimé ou le nœud tombe, le contrôleur crée un nouveau Pod (nouvelle IP, nouvel ID), potentiellement sur un autre nœud.

Ce projet n'était pas seulement une suite d'exercices techniques, mais la construction progressive d'une usine logicielle complète. Chaque partie a ajouté une brique essentielle pour passer d'un simple fichier JavaScript local à une application robuste et distribuée.

2. Transformation : Avant vs Après DevOps

Environnement "Ça marche sur ma machine" Iso/Prod grâce aux conteneurs (Immuabilité)

3. Les Piliers Techniques Maîtrisés

  • Immuabilité : Une fois construite, l'image Docker ne change jamais. On la promeut d'environnement en environnement.
  • Infrastructure as Code (IaC) : Toute l'infrastructure (K8s) et la configuration (Dockerfile, CI) sont décrites dans le code.
  • Automatisation : Suppression des tâches manuelles répétitives via GitHub Actions.
  • Observabilité & Résilience : L'application n'est pas juste "lancée", elle est "pilotée" par Kubernetes (Probes, ReplicaSet).

🎉 Conclusion Générale du Projet

Après avoir parcouru les 7 étapes de ce projet (Partie 0 à 6), nous avons réussi à transformer un environnement de développement vierge en une plateforme de déploiement cloud-native sophistiquée.

Rétrospective de l'Aventure

  • Partie 0 : Setup - Mise en place du socle technique (VSCode, Git, Node.js).
  • Partie 1 : Développement - Création de l'application "Calculatrice" avec tests unitaires (Jest) et qualité de code.
  • Partie 2 : Automatisation (CI) - Création du pipeline GitHub Actions pour valider chaque commit automatiquement.
  • Partie 3 : Conteneurisation - Packaging de l'application en image Docker légère et portable.
  • Partie 4 : Registre & Sécurité - Publication sur Docker Hub et scan de vulnérabilités.
  • Partie 5 : Orchestration (Local) - Coordination multi-services avec Docker Compose.
  • Partie 6 : Kubernetes (Prod) - Déploiement résilient, scalable et auto-réparateur.
