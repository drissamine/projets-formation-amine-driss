Présentation & Préparation de l'Application

Ce projet consiste à déployer étape par étape une application Javascript (Node.js) complète de calculatrice. Nous avons défini une architecture avec Express, organisé le code source src/ et implémenté des tests unitaires avec Jest.

Commandes du Terminal exécutées

# Création des dossiers du projet mkdir -p mon-app-js/src mon-app-js/tests # Initialisation du projet NPM cd mon-app-js && npm init -y # Installation des dépendances Backend & Métriques npm install express@^4.18.0 prom-client # Installation des dépendances de Test npm install --save-dev jest@^29.0.0 supertest@^6.3.0 # Validation locale de l'application npm test npm start
Résultat des tests
Les tests unitaires Jest pour les opérations mathématiques (Addition et Soustraction) du fichier utils.js passent avec succès. L'application est servie localement sur le port 3000 avec les endpoints de base /health/live fonctionnels.

Conteneurisation : Docker & Compose

L'application a été conteneurisée grâce à un Dockerfile optimisé utilisant une image de base légère node:18-alpine. Un environnement multi-conteneurs a été simulé via docker-compose.yml.

Commandes du Terminal exécutées

# Construction de l'image Docker locale docker build -t mon-app-js:1.0 . # Option 1 : Lancement pur via Docker docker run --rm -p 3000:3000 mon-app-js:1.0 # Option 2 : Construction et lancement via Docker Compose docker compose build docker compose up -d
Objectif de conception
L'utilisation du `.dockerignore` a permis de bloquer le transfert des paquets NPM inutiles et du dépôt Git vers le démon Docker. Le Compose permet d'injecter facilement des variables d'environnement (ex: LOG_LEVEL).

Audit de Sécurité des Images K8s (Trivy)

Analyse des vulnérabilités associées à l'image précédemment construite (CVE).

Commandes du Terminal exécutées

# Exécution de Trivy en tant que conteneur ciblant les failles HIGH et CRITICAL docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:latest image --severity HIGH,CRITICAL mon-app-js:1.0
1. Quelle est la source des failles (Node/Alpine vs Code) ?
Pour notre image de base node:18-alpine, la immense majorité des vulnérabilités proviennent soit du système d'exploitation Alpine sous-jacent (librairies système bas niveau), soit de dépendances globales obsolètes pré-installées avec Node, et assez rarement de notre propre code Javascript applicatif.
2. Quelles actions correctives proposez-vous pour réduire ces vulnérabilités ?
  • OS / Image Basique Déplacer l'image vers une version LTS plus récente de Node (ex: node:20-alpine) ou utiliser des images encore plus restreintes dites Distroless (sans OS Alpine).
  • Code Mettre à jour systématiquement les dépendances NPM via npm audit fix.
  • Intégrer directement un scan Trivy critique bloquant dans le pipeline CI/CD (Pipeline Fail).

Architecture Kubernetes (K8s)

Déploiement complet des microservices applicatifs sur un cluster K8s via des ressources distinctes écrites manuellement dans le dossier k8s/.

Commandes du Terminal exécutées

mkdir -p k8s # Application séquentielle des manifestes : kubectl apply -f k8s/01-namespace.yaml kubectl apply -f k8s/02-configmap-secret.yaml kubectl apply -f k8s/03-redis-service.yaml kubectl apply -f k8s/04-deployment.yaml
1. Pourquoi est-il important d'utiliser un namespace ? Différence avec un cluster ?
Un namespace permet l'isolation logique (ressources, droits, quotas) des applications au sein d'un même immense cluster physique/virtuel. Le cluster est l'infrastructure serveurs globale, le namespace est juste la "boîte" interne. Si on l'omet, Kubernetes installe tout dans le namespace default.
2. Quelle est la différence entre une Image Docker, un Conteneur et un Pod ?
L'Image est le code mort/lecture seule. Le Conteneur est une instance "vivante" de cette image. Le Pod est l'unité encapsulatrice globale de Kubernetes, pouvant faire tourner plusieurs conteneurs fortement couplés partageant IP/Stockage. Un Pod seul n'est jamais mis en prod car s'il meurt, il ne ressuscite pas (pas d'auto-guérison).
3. Logique Pod -> Service -> Deployment ?
On enveloppe l'application dans un Pod, mais comme son IP change souvent, on met un Service devant pour agir comme LoadBalancer fixe. Et pour gérer la recréation automatique de ces Pods éphémères s'ils crashent (Auto-healing) ou de faire des mises à jour sans downtime, on englobe tout cela via un puissant Deployment.
4. ConfigMap & Secrets ? Faut-il redémarrer les pods en cas de modif ?
Pour respecter l'hygiène "12 factors app", on dissocie la Config du Code. Les ConfigMaps gèrent le texte clair, et les Secrets gèrent les valeurs sensibles encodées en Base64. De base, modifier un Secret ou ConfigMap injecté en variable d'environnement nécessite un redémarrage artificiel explicite des Pods pour qu'il soit relu/pris en compte.

Haute Disponibilité, Scalabilité & État (Redis)

L'ajout de HPA (autoscaling Horizontal) sur notre Deployment, ainsi que le déploiement de Redis persistant lié via Service "Headless".

Commandes du Terminal exécutées

# Exécution du StatefulSet Redis et HPA kubectl apply -f k8s/05-hpa.yaml kubectl apply -f k8s/06-redis-statefulset.yaml # Stress Test réseau HTTP générant un pic CPU pour déclencher le HPA calculatrice while($true) { curl http://localhost:8081/heavy?ms=500; Start-Sleep -Milliseconds 100 }
1. Scalabilité Automatique : Scaler sur le CPU uniquement est-il suffisant ? Le cooldown ?
Non, pour un serveur lourdement I/O (réseau, téléchargement fichiers très lourds, attente BD), le programme attend beaucoup et le CPU paraît libre au système. Scaler via le CPU est insuffisant ici. De plus, toutes les règles de sizing intègrent un cooldown volontaire (≈ 5 min) limitant la fermeture anarchique des pods juste après un court rebond artificiel afin de stabiliser le réseau.
2. Auto-Healing: Que devient l'adresse IP du Pod recréé ? Qui gère cela ?
L'adresse IP change forcément. C'est le composant ReplicaSet sous-jacent au Deployment, qui agit comme un chien de garde et recrée un nouveau POD. Le Service réseau Kubernetes met ensuite à jour sa balance de charge sans perturber le client.
3. Quel est le rôle des Readiness Probes pendant un déploiement ?
La sonde Readiness interdit à l'équilibreur de charge d'envoyer votre trafic web au futur/nouveau pod, tant que l'applicatif n'a pas répondu OUI à son initialisation (base de données branchée, etc). Sans ça : erreur 502 / Temps d'arrêt.
4. Redis avec StatefulSet : Volume & Nom du pod créés ?
Un StatefulSet fige le réseau, les noms deviennent incrémentiels, propres et inaltérables : redis-0, redis-1... Le cluster de bdd est ainsi capable de se reconnaitre (maître/esclaves) en cas de crash. K8s alloue dynamiquement 1 Volume (PVC) différent personnellement dédié par Pod instancié (Via son VolumeClaimTemplate). Si redis-0 plante, il est recréé et retrouve le *même* disque qu'avant la mort.

Observabilité avec Prometheus

Analyse temps réel via les métriques /metric du serveur Node.js par l'opérateur Prometheus de façon très modulaire et découplée.

Commandes du Terminal exécutées

# Création du connecteur ("Service Monitor" CRD) récupérant la ressource custom kubectl apply -f k8s/07-servicemonitor.yaml # Exposer le port de Grafana post-install (Identifiants : admin/admin) kubectl port-forward svc/grafana 8082:3000 -n monitoring
1. Quel est l'avantage du ServiceMonitor face aux Annotations standard ?
Dans les grappes à forte volumétrie (centaines d'éditeurs), le ServiceMonitor (introduit par le pattern Operator Prometheus) autorise une ingénierie et un paramètrage total de l'Observabilité, en sélectionnant l'appli externe par ses Labels, isolant ainsi purement le travail des opérations et évitant une réécriture fastidieuse interne des manifestes Node bas niveau.
2. Pourquoi prioriser la métrique *nodejs_eventloop_lag_seconds* ?
Javascript/Node.js tourne en "Single Thread", exécutant les codes de façon asynchrone non-bloquante via son immense Event Loop (Boucle d'Événements). Dès qu'un lag critique s’observe sur cette boucle, cela signifie brutalement que le canal exécute une fonction énorme bloquante l'empêchant de traiter *absolument toute autre connexion web entrante future*, un déni de service !
3. Déclenchement de l'endpoint /heavy et impact sur le CPU Usage dans Grafana
En générant une charge intensive avec une commande comme while($true) { curl http://localhost:8081/heavy?ms=500; Start-Sleep -m 100 }, on bloque délibérément l'Event Loop. Dans Grafana, on observera une montée en flèche brutale du graphique de consommation CPU Usage (récupéré par Prometheus + cAdvisor). Dès que la consommation dépasse le seuil défini dans le HPA (ex: 50%), cela va déclencher un Scale Out (augmentation du nombre de réplicas de pods) afin de répartir la charge sur de multiples instances.
