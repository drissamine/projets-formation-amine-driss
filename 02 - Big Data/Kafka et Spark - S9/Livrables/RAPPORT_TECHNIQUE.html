Introduction et contexte

Ce projet met en œuvre un pipeline d'analyse en temps réel des habitudes de visionnage vidéo pour une plateforme de streaming. L'enjeu : ingérer un flux d'événements utilisateurs (PLAY, PAUSE, STOP, SEEK), le traiter à la volée avec Spark Structured Streaming, en tirer des agrégations et des alertes, puis stocker les résultats pour analyse.

Objectif atteint : pipeline complet, fonctionnel sur données réelles, sans warning, couvrant les 3 parties du sujet (simulation, traitement Spark, monitoring/optimisation).

Ingestion

Producteur Python → Kafka 3.7 (mode KRaft, sans Zookeeper) via Docker. Topic à 3 partitions, rétention 7 jours.

Traitement

Spark Structured Streaming : parsing/validation, 4 requêtes en fenêtres glissantes (10 min / 5 min), détection d'anomalies.

Stockage & visu

Console, fichiers CSV/JSON rangés par requête/date, base SQLite interrogeable, Kafka UI pour les topics.

2.2 Configuration Kafka (Tâche 1.2)

  • Topic streaming-events : 3 partitions, réplication 1, rétention 7 jours (retention.ms=604800000).
  • Topic streaming-events-dlq : dead-letter queue (messages invalides).
  • Mode KRaft (sans Zookeeper) — double listener : kafka:9092 (Docker) / localhost:29092 (host).

Étapes réalisées

 Tâche 1.1 · Infra

Étape 1 — Démarrage de Kafka avec Docker (mode KRaft)

Création du docker-compose.yml qui démarre deux services : Kafka 3.7 en mode KRaft (sans Zookeeper) et Kafka UI (Provectus) sur localhost:8080. Double listener configuré pour séparer le trafic Docker du trafic host (producteur et Spark lancés en local).

Vérification : docker ps indique le conteneur healthy, et kafka-broker-api-versions répond sur localhost:29092. Kafka UI accessible sur http://localhost:8080.

 Tâche 1.2 · Topics

Étape 2 — Création et configuration des topics Kafka

Création du topic principal streaming-events avec : 3 partitions (pour paralléliser la consommation), réplication 1 (mono-broker), rétention 7 jours. Création du topic DLQ streaming-events-dlq (1 partition) qui recevra les messages invalides en Tâche 3.2. Script create_topic.ps1/.sh idempotent.

Vérification : kafka-topics --describe confirme les 3 partitions et le retention.ms=604800000.
scripts/create_topic.ps1 scripts/create_topic.sh
 Tâche 1.1 · Schéma

Étape 3 — Générateur d'événements cohérents

Conception d'un EventGenerator qui produit des événements aléatoires mais cohérents : généralisation d'un catalogue de N vidéos (genre et durée fixes par video_id), tirage d'utilisateur parmi M, respect de current_time ≤ duration. 4 types d'événements, 3 genres, 3 devices. Injection optionnelle de messages corrompus pour la DLQ.

Le catalogue stable garantit des agrégations utilisables : un même video_id a toujours le même genre, ce qui rend l'analyse par genre (Tâche 2.2 - Requête 3) significative.
src/common/event_schema.py
 Tâche 1.1 · Producteur

Étape 4 — Producteur Kafka Python

Écriture de producer.py avec le client kafka-python. La clé de partitionnement est user_id : tous les événements d'un même utilisateur tombent dans la même partition (ordre préservé par utilisateur). Configuration robuste : acks=all, retries=5, linger_ms=20 (micro-batching), compression gzip. Gestion propre de Ctrl+C avec flush final.

Correction 1 : kafka-python 2.0.2 plante sur Python 3.14 (vendor.six.moves cassé). Montée à kafka-python ≥ 2.2. Correction 2 : kafka-python 3.x attend des sérialiseurs qui héritent de Serializer avec la signature serialize(self, topic, headers, data) — classes KeySerializer / JsonValueSerializer créées → 0 warning.
src/producer/producer.py
 Tâche 2.1 · Consommateur

Étape 5 — Consommateur Spark : parsing + validation

Mise en place de la SparkSession avec téléchargement automatique du connecteur Kafka spark-sql-kafka-0-10_2.12:3.5.1. EVENT_SCHEMA strict defini en StructType, puis parse_kafka_stream() décode le JSON et split_valid_invalid() sépare flux valide / invalide (JSON illisible, champ obligatoire manquant, event_type inconnu, timestamp invalide). Ajout de event_time (timestamp métier) et processing_time (ingestion Spark).

Problème Windows : Spark exige winutils.exe + hadoop.dll sur le FS local (même en mode console) → download des binaires Hadoop 3.3.6 et HADOOP_HOME forcé dans le projet.
src/consumer/spark_consumer.py src/common/spark_schema.py
 Tâche 2.2 · Agrégations

Étape 6 — Les 4 requêtes en fenêtres glissantes

Implémentation des 4 requêtes d'agrégation : fenêtre 10 min / slide 5 min + watermark 15 min (tolère le retard, borne l'état Spark).

  • Requête 1 — Popularité : vues (PLAY), events, users uniques par vidéo/fenêtre → Top-N par fenêtre via row_number() dans foreachBatch.
  • Requête 2 — Engagement : events, vidéos vues, proxy max−min(current_time), dernier event par user/fenêtre + utilisateurs inactifs (>15 min).
  • Requête 3 — Genre : répartition des vues + position moyenne par genre/fenêtre.
  • Requête 4 — Anomalies : DEVICE_EVENT_FLOOD (>1000 events / 5min / device) et USER_TOO_MANY_VIDEOS (>10 vidéos distinctes / 1h, fenêtre glissante 1h/10min).
Optimisation : le mode outputMode("complete") recalculait tout l'état à chaque micro-batch (timeout sur Top-N) → passage en update (incrémental). Approx : approx_count_distinct car les comptes distincts exactes ne sont pas supportés en streaming.
src/consumer/transformations.py
 Tâche 2.3 · Sorties

Étape 7 — Sorties console + fichiers CSV/JSON + SQLite

Une seule requête = un seul foreachBatch (un seul consumer Kafka par requête) qui route vers les destinations activées. Fichiers rangés par requête/date : results/<requete>/<AAAA-MM-JJ>/<requete>_<HHMMSS>.csv|.json. SQLite écrit via une table par requête, créée à la volée.

Problème Python 3.14 : toPandas() importe distutils, supprimé en Python 3.12+. → sorties réécrites sans pandas, via collect() + csv / json / sqlite3 de la stdlib. pandas retiré de requirements.txt.
src/consumer/sinks.py src/consumer/streaming_app.py
 Tâche 3.1 · Métriques

Étape 8 — Métriques de performance (throughput, latence, lag)

Mise en place d'un StreamingQueryListener qui, à chaque QueryProgress, expose le inputRowsPerSecond / processedRowsPerSecond (throughput) et le maxOffsetsBehindLatest (lag Kafka). Un foreachBatch séparé calcule la latence end-to-end (processing_time − event_time) sur les données réelles.

Mesures réelles (90 000 événements produits en parallèle, 34 micro-batches) : débit d'entrée ~567 evt/s, capacité Spark 2-4 k/s, latence moyenne ~2,5 s, lag Kafka = 0 (Spark absorbe le débit sans retard).
src/consumer/metrics.py src/consumer/metrics_app.py
 Tâche 3.2 · DLQ

Étape 9 — Dead-Letter Queue + checkpoints (reprise sur incident)

Reprise du flux invalide produit en Tâche 2.1, enrichissement avec une raison d'erreur (INVALID_JSON, MISSING_REQUIRED_FIELD, BAD_EVENT_TYPE, BAD_TIMESTAMP) et le contexte (partition/offset source, horodatages), puis republication dans le topic streaming-events-dlq via un sink Kafka. La requête utilise un checkpointLocation : en cas de crash, elle reprend là où elle s'était arrêtée (exactly-once côté offsets Kafka source).

Windows & espaces : Hadoop gère mal les espaces dans les URI de checkpoint → CHECKPOINT_DIR relocalisé dans C:\Users\driss\.tp-kafka-spark\checkpoints. Test de reprise : relance sans --reset ⇒ DLQ reste à 74 (avant = après), aucun reprocessing.

Choix techniques justifiés

Format des données

JSON sur Kafka : lisible, auto-descriptif, simple à déboguer dans Kafka UI. La clé = user_id préserve l'ordre par utilisateur. Sorties CSV (tableur), JSON (réutilisable), SQLite (SQL ad hoc) via la stdlib uniquement.

Taille des fenêtres

10 min / slide 5 min (énoncé) : le recouvrement lisse les agrégations et évite les effets de bord. Watermark 15 min borne l'état Spark. Fenêtres spécifiques pour les anomalies (1h/10min utilisateur, 5min tumbling pour le flood).

Stratégie de checkpoint

checkpointLocation activé (DLQ + option --checkpoint). Reprise exactly-once côté offsets Kafka source. Chemin sans espaces (problématique Windows/Hadoop). Effets de bord du foreachBatch = at-least-once (agrégations idempotentes par clé de fenêtre).

Mode de sortie & optimisations

  • outputMode("update") retenu (incrémental, performant) ; complete écarté (timeout sur Top-N).
  • Top-N par fenêtre via foreachBatch + row_number() (non exprimable directement sur un flux).
  • approx_count_distinct pour les comptes distincts (non supportés en exact sur un flux).
  • watch_time_proxy = max(current_time) − min(current_time) : approximation documentée pour les événements instantanés.

Améliorations potentielles

Avro + Schema Registry

Validation de schéma centralisée, messages plus compacts, évolution de schéma maîtrisée vers Avro/Protobuf.

Stockage analytique

Remplacer SQLite par PostgreSQL/ClickHouse ou un data lake (Parquet/Delta) pour la montée en charge et les requêtes analytiques.

Exactly-once bout en bout

Sink transactionnel (Kafka→Kafka transactionnel) ou idempotence applicative pour les effets de bord du foreachBatch.

Visualisation temps réel

Tableau de bord Grafana/Superset branché sur la base de résultats ou sur Prometheus pour les métriques.

Scalabilité horizontale

Cluster Spark multi-exécuteurs et Kafka multi-brokers (réplication > 1) pour la tolérance aux pannes.

Alerting

Publier les anomalies vers un canal (webhook, e-mail, Slack) au lieu de la seule console/base.

Modèle de temps de visionnage

Remplacer le proxy max−min(current_time) par une vraie reconstruction de session (flatMapGroupsWithState stateful).

Tests CI end-to-end

Kafka éphémère via Testcontainers automatisés en pipeline d'intégration continue.
